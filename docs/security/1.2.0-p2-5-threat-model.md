# Threat model: P2-5, the built-in single-owner authorization server

Author: Mark (security). Date: 2026-11-25. For: Ayush (implements P2-5), Dan (P2-6, P2-7), Violet (P2-11).
Status: part of the 1.2.0 spec (`docs/specs/1.2.0-remote-mode.md`, PR #57). Coding on P2-5 starts
from this document; the numbered requirements in section 6 are the acceptance bar for its PR.

## 1. What P2-5 is, in one paragraph

No2SQL in HTTP mode (P2-3) with auth (P2-4) is an OAuth 2.1 *resource server*: it checks a bearer
token on every `/mcp` request. ChatGPT and claude.ai can only obtain such a token through an OAuth
*authorization server*, so P2-5 adds a very small one inside the same process, at the same public
URL. It has exactly one human user, the owner, who proves identity with one password. Any OAuth
client that the owner approves on the consent page gets a token that reads the owner's MongoDB
(within `NO2SQL_ALLOWED_DATABASES`) until the owner revokes it. That sentence is the whole security
story: the consent page and the token lifecycle are what stand between the public internet and the
database.

## 2. Scope and assumptions

- One deployment, one owner, one MongoDB connection string (`NO2SQL_MONGO` or `NO2SQL_MONGO_FILE`).
  There are no other users, roles or tenants. Multi-user is out of scope (hosted phase).
- The server runs on the owner's host or container, behind a TLS-terminating reverse proxy or tunnel
  (Caddy, nginx, Cloudflare Tunnel, ngrok). `NO2SQL_PUBLIC_URL` is the `https://` URL clients type.
  Traffic between the proxy and Kestrel is plain HTTP on a trusted network (same host or the same
  Docker network). The proxy is trusted for `X-Forwarded-For` and `X-Forwarded-Proto` only when it is
  listed in `NO2SQL_HTTP_TRUSTED_PROXIES` (P2-6).
- Clients: ChatGPT (`https://chatgpt.com/connector_platform_oauth_redirect`, prefers CIMD), claude.ai
  (`https://claude.ai/api/mcp/auth_callback`, DCR or CIMD, 10-second limit on every discovery,
  registration and token call), Claude Code (loopback `http://127.0.0.1:<port>/...` redirect, DCR),
  the Responses API (bearer token from P2-4, does not use P2-5 at all), MCP Inspector for testing.
- The resource server and the authorization server share one process, one signing key set and one
  data directory. The resource server validates tokens the same way for P2-4's external IdP and for
  P2-5 (JWT, `iss`, `aud`, `exp`, signature), so P2-5 issues JWTs and publishes a JWKS.
- Single process. P2-5 keeps authorization codes and rate-limit state in memory; running two replicas
  behind one public URL is not supported in 1.2.0 and the README says so.
- The P2-6 hardening (Host and Origin checks, body limits, rate limits, security headers, no exception
  details) applies to every P2-5 endpoint too. This document names the extra limits P2-5 needs.

## 3. Assets, most valuable first

| # | Asset | Why it matters |
|---|---|---|
| A1 | Read access to the MongoDB databases (the data itself) | The only thing an attacker ultimately wants. Every tool is read-only, so the loss is confidentiality, not integrity |
| A2 | The MongoDB connection string | Full database credentials, usually broader than No2SQL's allow-list. Already protected by the 1.1.2 and P2-7 rules; P2-5 must never put it anywhere new |
| A3 | Owner password (`NO2SQL_OWNER_PASSWORD` or generated) | Grants consent for any client, so it is equivalent to A1 |
| A4 | Signing keys (private) | Forging any access token, equivalent to A1 for as long as the key lives |
| A5 | Refresh tokens | Long-lived access without the password; held by Anthropic/OpenAI and in our data directory |
| A6 | Access tokens | Short-lived access; travel on every `/mcp` request |
| A7 | Authorization codes | Convertible to tokens for 60 seconds if PKCE is bypassed |
| A8 | Client registrations and redirect URIs | Control where codes are sent and what the consent page shows |
| A9 | The owner's browser session during login and consent | A CSRF or clickjacking target |
| A10 | Availability | A public endpoint that does expensive MongoDB sampling; also the owner's ability to revoke |

## 4. Actors and trust boundaries

- **Internet attacker**: anyone who can reach the public URL. Can register clients (DCR is open by
  design, see section 5.2), request authorization, call the token endpoint, and make the server fetch
  URLs (CIMD).
- **Malicious or compromised OAuth client**: a registered client, or a real vendor whose token store
  is breached. Holds valid refresh tokens for as long as the owner has not revoked them.
- **Website in the owner's browser**: can navigate the owner to our authorize endpoint, embed our pages
  in frames, or submit forms to us. Cannot read our responses (same-origin policy) unless we send CORS
  headers, which we never do.
- **Local or container-level reader**: sees environment variables (`docker inspect`), process listings
  and, with the right permissions, the data directory and container logs. Out of scope for the
  server to defend against, but it shapes what we write where (section 5.6).
- **Network attacker between proxy and app**: assumed not present (same host or Docker network).
  Documented as an assumption, not defended.

## 5. Threats and required mitigations, by component

Each row is a threat; the mitigation column is normative ("must"). R-numbers point to section 6.

### 5.1 Discovery metadata (RFC 8414 at `/.well-known/oauth-authorization-server`, PRM at `/.well-known/oauth-protected-resource`, JWKS)

| Threat | Mitigation |
|---|---|
| Host header injection makes the server advertise an attacker-controlled issuer, endpoints or JWKS URL, poisoning a client's cached metadata | Every URL in metadata is built from `NO2SQL_PUBLIC_URL`, never from the request's `Host`, `X-Forwarded-Host` or scheme. P2-6's host allow-list rejects unknown hosts before the request reaches us (R1) |
| Clients downgrade to weak options because we advertise them | Advertise exactly: `response_types_supported: ["code"]`, `grant_types_supported: ["authorization_code","refresh_token"]`, `code_challenge_methods_supported: ["S256"]`, `token_endpoint_auth_methods_supported: ["none"]`, `client_id_metadata_document_supported: true`, `scopes_supported` (the fixed list), `registration_endpoint` (R2). Nothing else |
| Private key exposure through the JWKS | JWKS contains public parameters only (`kty`, `crv`, `x`, `y`, `kid`, `use`, `alg`). A unit test asserts no `d` field (R27) |
| Metadata served over plain HTTP in production | Built-in AS refuses to start unless `NO2SQL_PUBLIC_URL` is `https://`, or it is a loopback `http://` URL for local testing (R3) |

### 5.2 Dynamic Client Registration (RFC 7591, open, unauthenticated by design)

The registration endpoint is open because ChatGPT, claude.ai and Claude Code register on their own.
That makes it the cheapest thing an attacker can hit. The owner, not the registration, is the gate:
a registration grants nothing until the owner approves it on the consent page.

| Threat | Mitigation |
|---|---|
| Registration flooding fills the data directory or memory | Cap stored clients (default 200). When full, evict clients that were never approved, oldest first; if none, return `429` with `Retry-After`. Approved clients are never evicted. Per-IP rate limit on `POST /register` (default 10 per hour) plus the global limiter (R4) |
| `redirect_uris` that let a code leak: `javascript:`, `data:`, `http://` to a public host, wildcards, fragments, userinfo, or a different host than the client later uses | Accept only `https://` URIs with no fragment and no userinfo, or loopback `http://127.0.0.1`, `http://[::1]` and `http://localhost` with any port (RFC 8252 section 7.3). Reject custom schemes. Store the exact strings; matching at authorize time is exact except that the loopback port may vary (R5) |
| Consent-page phishing through `client_name` ("ChatGPT", "Anthropic Claude") on an attacker's registration | DCR clients are shown as **unverified** on the consent page, with the registered `client_name` HTML-escaped and limited to 64 printable characters, next to the redirect host in bold. CIMD clients are shown by their verified host. The copy says what approval grants (R6, R13) |
| SSRF or tracking through `logo_uri`, `jwks_uri`, `policy_uri`, `tos_uri`, `software_statement` | Never fetch any URL from a registration. Store `client_name`, `redirect_uris`, `client_uri` (display only, escaped) and drop everything else. Reject `token_endpoint_auth_method` other than `none` and reject a request that asks for `client_secret` semantics; we issue no secrets (R7) |
| Registration response reveals internal state | Return only `client_id`, `client_id_issued_at`, `redirect_uris`, `token_endpoint_auth_method`, `grant_types`, `response_types`. No `registration_access_token`, no management endpoint in 1.2.0 (R7) |
| Oversized or hostile JSON | Body limit 16 KiB on this endpoint, `Content-Type: application/json` required, depth-limited parsing (System.Text.Json default depth 64 is fine), unknown members ignored (R4) |

### 5.3 Client ID Metadata Documents (CIMD)

With CIMD the `client_id` is an `https://` URL that we fetch. This is a server-side request to an
attacker-chosen URL, so it is an SSRF primitive and an amplification primitive by construction.

| Threat | Mitigation |
|---|---|
| SSRF into the owner's network: `client_id` pointing at `http://`, an IP literal, `localhost`, RFC 1918 or link-local ranges, the cloud metadata address `169.254.169.254`, or the MongoDB host itself | Fetch only if: scheme is `https`, port is 443 (or absent), host is a DNS name (not an IP literal, not `localhost`, not ending in `.local`/`.internal`/`.localhost`), and **every** resolved address is public (reject loopback, private, link-local, multicast, unique-local, unspecified, IPv4-mapped forms of those, and documentation ranges). Validate the resolved addresses inside the connection callback (`SocketsHttpHandler.ConnectCallback`) so the connection goes to the address that was checked, which closes the DNS-rebinding race (R8) |
| Redirect-based SSRF (`https://good.example/x` redirects to `http://10.0.0.5/`) | Do not follow redirects (`AllowAutoRedirect = false`). A 3xx is a fetch failure (R8) |
| Slow-loris or huge documents tie up the server, or push the client past its 10-second budget | Connect timeout 3 s, total timeout 5 s, response body cap 64 KiB, `Content-Type` must be `application/json`. One fetch at a time per host, at most 10 CIMD fetches per minute globally; a failed fetch is cached as a failure for 5 minutes (R9) |
| Amplification: attacker makes us hammer a third party | The same global limit (10/min) and the failure cache; never retry (R9) |
| Document mismatch or spoofing | The document's `client_id` must equal the URL we fetched, byte for byte. `redirect_uris` must be present and every URI must be `https://` on the **same host** as the `client_id` URL (ChatGPT and claude.ai both satisfy this), or loopback as in 5.2. `token_endpoint_auth_method` must be `none`. Anything else is a rejected client (R10) |
| Stale or poisoned cache | Cache successful documents for at most 1 hour keyed by exact URL, in memory only. Re-fetch on expiry. Never persist CIMD documents (R9) |
| Private hosts reachable through a proxy variable | The CIMD `HttpClient` ignores `HTTP_PROXY`/`HTTPS_PROXY` environment (`UseProxy = false`) so the address check is meaningful (R8) |

### 5.4 Authorization endpoint, login and consent

| Threat | Mitigation |
|---|---|
| Open redirect: an attacker sends the owner to `/authorize?redirect_uri=https://evil/` | Validate `client_id` and `redirect_uri` **before anything else**. If the client is unknown or the URI does not match a registered one, render a plain error page with no redirect and no link containing the URI. Only after both validate may any error be returned by redirect (R11) |
| PKCE downgrade or omission; an attacker who steals a code uses it | Require `code_challenge` (43 to 128 characters of the unreserved set) and `code_challenge_method=S256`. Reject `plain`, reject missing. The code is bound to the challenge (R12) |
| Audience confusion: a token meant for another resource used here | Require the `resource` parameter (RFC 8707) and require it to equal the public MCP URL exactly (`NO2SQL_PUBLIC_URL` + `/mcp`, trailing-slash-insensitive). Otherwise `invalid_target`. The token's `aud` is set from config, not from the request (R12) |
| Unknown or wrong `response_type`, `scope` or oversized parameters | `response_type` must be `code`. Scopes must be a subset of the fixed list (`mcp:tools`, `offline_access`); unknown scopes are an error, not silently dropped. Each query parameter is capped at 2 KiB and the whole query at 8 KiB. `state` is echoed back unchanged (R12) |
| Password brute force | Compare with `CryptographicOperations.FixedTimeEquals` on UTF-8 bytes. After 5 failures from one IP, delay responses 2 s doubling to 60 s and stop at 20 per hour per IP; also a global cap of 100 failures per hour across all IPs (a distributed attack then locks login for everyone for the rest of the hour, which is the right trade for a single-owner server). Failures are logged with IP and timestamp, never with the attempted password (R14) |
| Weak or leaked owner password | If `NO2SQL_OWNER_PASSWORD` is set it must be at least 12 characters, otherwise the server refuses to start with a message that names the variable. If it is not set, generate 24 characters from a 62-symbol alphabet (about 143 bits) with `RandomNumberGenerator`, print it **once** to stderr framed by a clear notice, and store only its SHA-256 in the data directory so later starts do not print it again. The README warns that container logs keep that line (R15) |
| Session fixation and cookie theft during login | After a successful login issue a new random session id (32 bytes), cookie `__Host-no2sql_owner`, `HttpOnly`, always `Secure` (browsers accept Secure cookies on `http://localhost`), `SameSite=Strict`, `Path=/`, lifetime 10 minutes, stored server-side in memory with the owner flag. Login only ever happens as a step inside an authorize request, so `Strict` costs nothing (R16) |
| CSRF on the consent POST: a website in the owner's browser submits "approve" for the attacker's client | Consent form carries a random anti-forgery token bound to the owner session and the pending authorization request; the POST must carry the cookie, the token, and an `Origin` (or `Referer`) header equal to the public URL's origin; `SameSite=Strict` is a second layer. Approve is POST only; GET never changes state (R17) |
| Clickjacking the consent button | `Content-Security-Policy: default-src 'none'; style-src 'self'; img-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'` and `X-Frame-Options: DENY` on every HTML page. No inline scripts, no scripts at all; the pages are two forms (R18) |
| The owner approves the wrong client because the page is ambiguous | The consent page shows, in this order: who is asking (CIMD: the verified host, for example `chatgpt.com`; DCR: "Unverified client: <client_name>"), where the code will be sent (redirect host, bold; a loopback redirect is labelled "an app on your computer"), what is granted ("read your MongoDB databases through No2SQL until you revoke it"), the requested scopes, and two buttons. DCR clients are **always** asked; a CIMD client that was approved before may be re-approved without the page only if the same `client_id` and `redirect_uri` are presented and the earlier approval is less than 30 days old (R13) |
| Authorization code guessing or replay | Codes are 32 random bytes, base64url, single use, 60-second lifetime, stored in memory as SHA-256 hashes with client id, redirect URI, challenge, scope, resource and the issue time. The server rejects a second use and, per RFC 6749 section 4.1.2, revokes every token already issued from that code (R19) |
| Reflected XSS through `client_name`, `state`, `error_description` or `redirect_uri` | Everything rendered is HTML-encoded by Razor or `HtmlEncoder`; the error page never prints `redirect_uri` or `state`; `error_description` on redirects is a fixed string per error code (R18) |

### 5.5 Token endpoint and tokens

| Threat | Mitigation |
|---|---|
| Wrong content type or JSON body tricks a parser | Accept only `application/x-www-form-urlencoded`, body cap 16 KiB, `POST` only, `Cache-Control: no-store` and `Pragma: no-cache` on every response (R20) |
| Code stolen in transit or from logs, then redeemed by the attacker | `code_verifier` must hash to the stored challenge (S256). `client_id` and `redirect_uri` must equal the code's. Codes expire in 60 s. The code, verifier and tokens never appear in logs (R19, R28) |
| Refresh token theft from a vendor breach or our data directory | Refresh tokens are 32 random bytes, stored as SHA-256 hashes with client id, scope, family id, issue and expiry times. Every refresh rotates: a new refresh token is issued and the old one is marked used. Presenting a used token revokes the entire family (RFC 9700 section 4.14.2 reuse detection). Absolute lifetime 30 days, after which the client must go through consent again. `resource` on refresh, if present, must equal the MCP URL (R21) |
| Access token theft; forged or confused tokens accepted by the resource server | Access tokens are JWTs signed with ES256 (P-256) and `kid`; claims `iss` (= public URL), `sub` (= `owner`), `aud` (= the MCP URL, a single string), `client_id`, `scope`, `jti`, `iat`, `exp` (default 60 minutes, configurable 5 to 1440), header `typ: at+jwt`. The resource server validates signature against the current JWKS only, `iss` exact, `aud` exact, `exp` with at most 60 s skew, `typ`, and rejects `alg: none` and every HMAC algorithm by configuring the allowed algorithm list (R22) |
| Revocation does not work because JWTs are stateless | `no2sql oauth revoke-all` (a CLI command; there is no HTTP admin endpoint in 1.2.0) deletes all refresh tokens, deletes all DCR registrations that were never approved, and replaces the signing key set without a grace period, so every outstanding access token fails `kid` lookup. The running server notices the changed files within a second (mtime check, R23), so no restart is needed. The owner also has `no2sql oauth list` to see clients and `no2sql oauth revoke <client_id>` for one client (deletes its refresh tokens and approval) (R23) |
| Token endpoint brute force or flooding | Per-IP limit 30 per minute, global limiter from P2-6, constant-time comparisons everywhere, identical error timing for "unknown code" and "bad verifier" (both `invalid_grant`) (R20) |
| Error responses leak internals | Only RFC 6749 error codes with fixed `error_description` strings. Exceptions become `server_error` with an error id logged server-side (R24) |

### 5.6 Keys, storage and the data directory

| Threat | Mitigation |
|---|---|
| Private key readable by other local users | `NO2SQL_DATA_DIR` (default `~/.no2sql` outside Docker, `/data` in the image, intended for a volume). Created with mode `0700`; every file written with `0600` via `File.SetUnixFileMode` on Unix and an explicit DACL for the current user on Windows. On start, if the directory or key file is more permissive, log a warning naming the path (refuse to start if the key file is world-readable) (R25) |
| Key loss or corruption bricks the deployment | Key generation and every store write go to a temp file then `File.Move` with overwrite, so a crash leaves either the old or the new file. If the key file exists but cannot be parsed, the AS refuses to start with a message pointing at `revoke-all` rather than silently generating a new key (R26) |
| Old key kept forever | Routine rotation: `no2sql oauth rotate-keys` creates a new signing key and keeps the previous public key in the JWKS for the access-token lifetime plus 60 s, then drops it. The README recommends rotating yearly and after any suspected compromise (R26) |
| Refresh tokens or codes in plain text on disk | Only SHA-256 hashes of refresh tokens are stored. Authorization codes are never written to disk. The owner password is stored only as a hash and only when it was generated (R21, R15) |
| Backups and snapshots leak the directory | README: the data directory contains the signing key and refresh-token hashes; treat backups of it like a password file, and run `revoke-all` if a backup is lost (R29) |
| Data directory served as static content | HTTP mode registers no static file middleware and no directory browsing; the data directory is never under a served path (P2-6 acceptance criterion 10) |

### 5.7 Cross-cutting

| Threat | Mitigation |
|---|---|
| Secrets in logs | Never log: passwords, codes, verifiers, challenges, access tokens, refresh tokens, `Authorization` or `Cookie` headers, request bodies of `/token`, `/register` or `/login`. Log: endpoint, client id (or CIMD host), outcome, error code, IP, duration (R28) |
| Clock skew between us and the clients | `exp` checks allow 60 s. The server logs a warning at start if its clock differs from the `Date` header of the first CIMD fetch by more than 5 minutes (optional, nice to have) |
| The 10-second client budget | Every P2-5 endpoint must answer within 2 s in normal operation; the only network call (CIMD fetch) is capped at 5 s and cached. Violet measures metadata, register, authorize (to the login page), token (R30) |
| Owner enables the AS on a loopback-only bind by mistake | If `NO2SQL_OAUTH_BUILTIN=true` and `NO2SQL_PUBLIC_URL` is loopback, log a notice that only local clients can reach it. If the public URL is non-loopback `http://`, refuse to start (R3) |
| Both the built-in AS and an external IdP configured | Refuse to start; exactly one of `NO2SQL_OAUTH_BUILTIN`, `NO2SQL_OAUTH_AUTHORITY`, `NO2SQL_HTTP_TOKEN` may be set, except that `NO2SQL_HTTP_TOKEN` may coexist with either OAuth mode for the Responses API (R3) |

## 6. Requirements (the acceptance bar for the P2-5 PR)

Discovery and configuration
- R1 All metadata URLs derive from `NO2SQL_PUBLIC_URL`; nothing from request headers.
- R2 AS metadata is exactly this key set, nothing more: `issuer`, `authorization_endpoint`, `token_endpoint`, `jwks_uri`, `registration_endpoint`, `scopes_supported` (`["mcp:tools","offline_access"]`), `response_types_supported` (`["code"]`), `grant_types_supported` (`["authorization_code","refresh_token"]`), `code_challenge_methods_supported` (`["S256"]`), `token_endpoint_auth_methods_supported` (`["none"]`), `client_id_metadata_document_supported` (`true`). Protected resource metadata is exactly: `resource`, `authorization_servers` (one entry, the issuer), `scopes_supported`, `bearer_methods_supported` (`["header"]`), `resource_name` (`"No2SQL"`).
- R3 Startup refuses: built-in AS without an `https://` (or loopback `http://`) public URL; more than one OAuth mode; a supplied owner password shorter than 12 characters.

Registration
- R4 `POST /register`: `application/json` only, 16 KiB cap, 10 per hour per IP, 200 stored clients with eviction of never-approved ones.
- R5 Redirect URIs: `https://` without fragment or userinfo, or loopback `http://` with any port; exact match otherwise.
- R6 DCR clients are labelled unverified on the consent page; `client_name` escaped and capped at 64 printable characters.
- R7 No URL from a registration is ever fetched; only `client_name`, `redirect_uris`, `client_uri` kept; `token_endpoint_auth_method` must be `none`; no secrets or management tokens issued.

CIMD
- R8 Fetch only `https://` on port 443 to a DNS name; every resolved address must be public, checked in the connect callback; no redirects; no proxy.
- R9 Connect 3 s, total 5 s, 64 KiB body, `application/json`; 10 fetches per minute globally; success cache 1 hour, failure cache 5 minutes, in memory only; no retries.
- R10 Document `client_id` equals the fetched URL; `redirect_uris` are `https://` on the same host as the `client_id` (or loopback); `token_endpoint_auth_method` is `none`.

Authorize, login, consent
- R11 Unknown client or unregistered `redirect_uri` renders an error page; no redirect, no echo of the URI.
- R12 `response_type=code`, `code_challenge` with `S256` required, `resource` required and equal to the MCP URL, scopes from the fixed list, per-parameter 2 KiB and total 8 KiB caps.
- R13 Consent page shows verified host or "Unverified client", redirect host, what is granted, scopes; DCR clients always prompt; CIMD re-approval without prompt only for the same `client_id` and `redirect_uri` within 30 days.
- R14 Constant-time password compare; per-IP backoff from 2 s to 60 s after 5 failures, 20 per hour per IP, 100 per hour globally; failures logged without the password.
- R15 Generated password: 24 characters, 62-symbol alphabet, printed once, stored as SHA-256 only.
- R16 Owner session: new 32-byte id at login, `__Host-` cookie, `HttpOnly`, always `Secure` (the `__Host-` prefix requires it; browsers accept Secure cookies on `http://localhost`), `SameSite=Strict`, 10 minutes.
- R17 Consent is POST only with an anti-forgery token bound to session and request, and an `Origin`/`Referer` check.
- R18 All HTML pages: the CSP in 5.4, `X-Frame-Options: DENY`, no scripts, every dynamic value HTML-encoded, fixed `error_description` strings.
- R19 Codes: 32 random bytes, 60 s, single use, stored as hashes with client, redirect URI, challenge, scope, resource; reuse revokes tokens issued from the code.

Tokens
- R20 `POST /token`: form-encoded only, 16 KiB cap, 30 per minute per IP, `Cache-Control: no-store`, identical errors for unknown code and bad verifier.
- R21 Refresh tokens: 32 random bytes stored as SHA-256 with a family id; rotation on every use; reuse revokes the family; 30-day absolute lifetime.
- R22 Access tokens: ES256 JWT with `kid`, `typ: at+jwt`, `iss`, `sub`, `aud` (single string = MCP URL), `client_id`, `scope`, `jti`, `iat`, `exp` (default 60 min); the resource server allows only ES256, checks `iss`, `aud`, `exp` (60 s skew) and `typ`. Key file: `<data dir>/signing-keys.json`, a JWK Set (RFC 7517) whose entries carry the private key (`d`), `kid`, `kty: EC`, `crv: P-256`, `alg: ES256`, `use: sig`, `status` (`active` or `retiring`) and, for retiring keys, `retire_at` (ISO 8601). Tests sign with the active key read from this file.
- R23 `no2sql oauth list`, `revoke <client_id>`, `revoke-all` and `rotate-keys` exist as CLI commands that write the data directory. A running server picks them up **without a restart**: on each token validation and each refresh it checks the modification time of `signing-keys.json` and `refresh-tokens.json` (at most once per second, cached in between) and reloads a changed file before deciding. `revoke-all` deletes all refresh tokens, deletes never-approved DCR clients and replaces the key set with one new active key and no retiring key, so every outstanding access token fails `kid` lookup within a second. `rotate-keys` adds a new active key and marks the old one `retiring` with `retire_at` = now + access-token lifetime + 60 s. If the CLI cannot write the data directory it refuses and says which path.
- R24 Error bodies carry RFC 6749 codes and fixed descriptions; unexpected exceptions become `server_error` with a logged error id. The exception path is proven by a unit test that registers a throwing endpoint in the test host only; the shipped binary has no fault hook.

Storage
- R25 Data directory `0700`, files `0600` (DACL on Windows); warning on looser modes, refusal if the key is world-readable.
- R26 Atomic writes; unparseable key file refuses to start; `rotate-keys` keeps the old public key for the access-token lifetime plus 60 s.
- R27 JWKS has public parameters only (test asserts no `d`).

Cross-cutting
- R28 No password, code, verifier, token, `Authorization`, `Cookie` or `/token`, `/register`, `/login` body in any log line.
- R29 README security note covers: what the built-in server protects, the data directory and backups, the generated password in container logs, how to rotate and revoke, and when to use an external IdP instead.
- R30 Metadata, register, authorize and token endpoints answer within 2 s (median of 5) in Violet's test; the CIMD fetch is the only outbound call and is bounded by R9.

Testability (from Violet's QA review of this document)
- R31 Every clock in P2-5 (code lifetime, approval memory, refresh-token lifetime, token `iat`/`exp`, rotation grace, rate-limit windows) comes from an injected `TimeProvider`, so unit tests advance time instead of waiting.
- R32 The CIMD address policy (R8) is a small internal interface with the production implementation as default. The `No2SQL.Tests` project (xUnit + `Microsoft.AspNetCore.Mvc.Testing`, created in P2-3) replaces it and the DNS resolver through `InternalsVisibleTo` only; nothing in environment variables or configuration can loosen it. R9, R10 and the post-resolution part of R8 are proven by those unit tests (stub resolver returning `169.254.169.254`, a stalling listener, a 302, a 100 KiB body, a wrong-host redirect URI). CI keeps the black-box literal rejections (`http://`, IP literals, `localhost`). The positive CIMD flow is a manual test against real ChatGPT.

## 7. Residual risks (accepted, documented in the README)

- Any client the owner approves can read everything the connection string and allow-list permit.
  There is no per-client scoping of databases in 1.2.0. The README recommends a read-only MongoDB
  user and `NO2SQL_ALLOWED_DATABASES` for every public deployment.
- Refresh tokens live in the vendor's systems. A breach there gives read access until the owner runs
  `revoke-all`; the 30-day absolute lifetime bounds it.
- No second factor on the owner login. The rate limits make online guessing impractical for a
  12-character password; an owner who picks a dictionary word is not protected.
- Environment variables are visible to anyone who can inspect the process or container. `NO2SQL_MONGO_FILE`
  (P2-7) and Docker secrets are the mitigation, and the same applies to `NO2SQL_OWNER_PASSWORD`; a
  future `NO2SQL_OWNER_PASSWORD_FILE` is a cheap follow-up.
- Plain HTTP between the proxy and Kestrel is trusted. Anyone on that network segment can read tokens.
- The server is single-instance. Two replicas would not share codes, sessions or rate-limit state.

## 8. Tests Violet should add for P2-5 (feeds P2-11)

1. `code_challenge_method=plain` and a missing `code_challenge` are both rejected with `invalid_request`.
2. `redirect_uri` not registered: response is an HTML error page (status 400), with no `Location` header and the URI absent from the body.
3. `resource` missing or pointing at another URL: `invalid_target`.
4. Authorization code used twice: second call `invalid_grant`, and the access token from the first call is rejected by `/mcp` afterwards.
5. Refresh token used twice: second call `invalid_grant`, and the newer refresh token from the family is rejected too.
6. Tokens signed with the active key from `signing-keys.json` but wrong in one way each: `aud` of another URL, `typ: JWT` where `at+jwt` is required for built-in tokens, `exp` 61 s in the past: `/mcp` answers 401 with `WWW-Authenticate`; `exp` 30 s in the past is accepted (skew).
7. `alg: none` and `HS256` tokens signed with the public key bytes: 401.
8. CIMD `client_id` of `http://…`, `https://127.0.0.1/…`, `https://10.0.0.1/…` and `https://localhost/…`: rejected black-box in CI. A hostname resolving to `169.254.169.254` (stub resolver), a URL that 302-redirects, a 100 KiB document and a server that stalls 10 s: rejected in unit tests (R32), and the authorize response arrives within 6 s.
9. CIMD document whose `redirect_uris` are on a different host than the `client_id`: rejected (unit test, R32).
10. DCR with `redirect_uris: ["javascript:alert(1)"]`, `["https://evil/#frag"]`, `["http://evil/"]`: rejected; `["http://127.0.0.1:0/cb"]` and `["https://claude.ai/api/mcp/auth_callback"]`: accepted.
11. 11th registration from one IP within an hour: 429 with `Retry-After`. 201st client when none is approved: 429. Multi-IP cases (this one, and R14's 100 per hour global cap) run with `NO2SQL_HTTP_TRUSTED_PROXIES=127.0.0.1` and a varying `X-Forwarded-For`; that is the intended route.
12. Six wrong passwords from one IP: the sixth response takes at least 2 s; the 21st within the hour is refused without checking.
13. Consent POST without the anti-forgery token, or with an `Origin` of another site: 403, and no code is issued.
14. Every HTML response carries the CSP with `frame-ancestors 'none'` and `X-Frame-Options: DENY`; every `/token` response carries `Cache-Control: no-store`.
15. Request with `Host: evil.example` and with `X-Forwarded-Host: evil.example` from an untrusted address: metadata still shows the configured public URL (or the request is rejected by P2-6).
16. The JWKS document contains no `d`; the data directory and key file have the required modes after first start.
17. After `revoke-all` run as a separate process while the server keeps running: within 2 s an outstanding access token and an outstanding refresh token are both rejected, with no restart. After `rotate-keys`: the old token keeps working until its `exp`, and a token minted afterwards carries the new `kid`.
18. The full log of a run containing a login, a consent, a code exchange and a refresh contains none of: the password, the code, the verifier, either token, the word `Bearer` followed by a token, or the connection string.
19. End to end with real ChatGPT and claude.ai, through a tunnel: connect, list tools, call `list_databases`, wait past the access-token lifetime, call again (refresh works), then `revoke-all` and confirm the next call fails.
